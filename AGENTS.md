# Capri development rules

## Tools and skills

- Author all new first-party tool contracts and Skills in English. When revising an existing contract, use English for the instructions being changed. Migrate unrelated legacy content through the planned tool review rather than expanding a small task into a repository-wide rewrite.
- Model-facing tool names, parameter and action descriptions, usage guidance, examples, result semantics, and application-authored diagnostic messages must be English. Prefer stable English identifiers and error codes; preserve compatibility with existing calls and checkpoints.
- First-party tool display names and action labels in the Tools catalog and chat activity must also be English. Keep the rest of the application UI localized.
- First-party Skills, including Skills generated by Capri, must use English metadata, instructions, examples, and supporting guidance. This requirement must also be reflected in the Skill creation path when implementing the planned migration.
- This rule does not translate user content, command output, quoted source material, or imported third-party Skills and MCP definitions. Keep user-facing UI localization and Capri's personality unchanged unless the user requests otherwise.

## Quality and efficiency

- Keep contracts concise and precise: purpose, when to use the tool, required inputs, consequential limits, side effects, and result interpretation. Include a valid example only when it resolves ambiguity. Avoid repeated instructions, boilerplate, and parallel Chinese/English copies.
- Keep schemas, runtime validation, dispatch, and documentation consistent. Make failures and partial results explicit; a successful tool invocation does not establish that the user's task succeeded.
- Prefer direct file operations, bounded outputs, useful batching, and reuse of existing environment evidence. Avoid redundant inspection, polling, dependency installation, and verification. Preserve session isolation, permission checks, cancellation, and recovery semantics.
- Validate meaningful behavior and compatibility. Compare correctness, invalid calls, repeated operations, context cost, and measured latency; do not assume English alone improves performance or optimize call count at the expense of correctness.
