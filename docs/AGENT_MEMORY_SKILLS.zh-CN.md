# Capri 记忆、Skills 与经验复用

2026-11-02：第八项六个子项首版实现。复用现有记忆存储、历史检索、TaskState、文件规则和 Skill 导入器；与进行中的 Skill 专项通过版本及来源接口衔接。本轮不连接、安装或操作手机，真机资源与交互验收仍待补。

## 8.1 数据归属与证据

| 内容 | 归属 | 写入与使用边界 |
| --- | --- | --- |
| 用户事实、偏好、未完约定 | `personal_memory` | 只在默认个人对话写入；任务对话只读；引用真实用户消息 |
| 项目规则、用户要求保留的资料／笔记 | `knowledge`、项目规则文件 | 显式保存；默认当前聊天，跨聊天共享沿用现有授权要求 |
| 安装、依赖、权限与网络事实 | `environment` | 现有作用域、有效期、指纹和实际执行证据，不改存个人记忆 |
| 当前目标、计划、纠正、进度 | `task_state`、任务检查点 | 随任务与历史版本保存，不自动升级为长期事实 |
| 可复用操作经验、Skill 使用观察 | `task_experience`、Skill 版本档案 | 从有工具证据的任务形成候选；加载、使用、成功与因果分别解释 |

`MemoryPolicy` 在提示中统一上述归属。新增个人笔记分类为 `user_fact / preference / open_item`；知识笔记分类为 `user_fact / project_rule / task_note`。环境事实、流程和当前进度不能通过这些分类伪装成永久用户事实。旧记录继续读取并标为 `legacy_unclassified`，不对旧内容进行猜测性重分类。

新个人记忆来源包含聊天、消息稳定 ID、角色、时间与原文摘要值。召回始终核对当前个人时间线，原文改变或来源被删除后停止使用；对话摘录仍然只是有来源的摘录，不把 Capri 自己说过的话当成已发生事实。项目笔记的来源也增加消息 ID 和摘要值，原有明确保存的资料仍保留其独立资源语义。

## 8.2 有容量上限的精选记忆

保留每条 1,600 字符、最多 200 条精选个人笔记的限制，并加入 32,000 字符总文本预算；检查与保存处于同一原子存储操作中。超过预算需要合并或忘记旧条目，不静默淘汰仍有效的重要用户信息。旧版本超额数据不直接删除，允许逐步缩小、合并和清理。

`remember` 可提供：

- `key`：稳定的英文主题标识。同一主题纠正更新原条目，避免新旧偏好同时注入。
- `expected_revision`：防止按旧版本覆盖刚发生的修改；旧调用不提供此字段仍兼容。
- `expires_at`：毫秒时间戳，0 表示无到期时间。到期事项不再召回。
- `category`：以上三种个人笔记分类，缺省兼容 `user_fact`。

`forget(id)` 停用精选笔记，保留原聊天消息；再次记住同一主题必须有忘记之后的新用户来源，不能重放旧来源恢复。到期主题同样需要新用户来源才能续期。旧来源不能覆盖更新的纠正。更正或遗忘笔记时，同一旧用户来源形成的自动摘录停止召回，重复保存摘录也不会将其重新激活，避免从另一份旧摘要重新带回该事实；原始历史仍可按显式历史请求查阅。来源已失效的笔记在后续保存时转为不可召回状态，释放精选容量；此清理与新记录一并提交，失败不会留下半条新记忆。遗忘／到期／来源失效的退役索引最多保留 200 条，对话摘录索引仍最多 1,000 条；这些上限不是删除原聊天原文的承诺。

来源存在与摘要匹配能约束溯源，不能自动证明模型概括忠于原意或判断两个不同主题键之间的语义矛盾。当前用户纠正与原文仍优先；没有新增自动付费整理模型。

## 8.3 历史检索后再回答

明确提及“上次／之前／还记得／last time”等过去事件时，`MemoryContext` 在本轮请求准备阶段直接做已有历史文本检索，不增加一次模型请求。默认使用用户已授权读取的当前已存时间线；“这个对话／this chat”缩小到当前聊天。不搜索被历史编辑移除的后缀，不读取其他聊天工作区，也不把当前提问本身当成检索命中。

自动提供最多 4 条、每条最多 500 字符的摘录，带聊天、时间线、消息稳定 ID、角色与原文摘要值。用户陈述与助手主张有不同含义；历史“构建成功”的一句话不是实际构建证据。需要完整依据时继续用 `conversation_history.read` 或当前任务的 `context_history` 读取原文／归档。没有命中只表示此次词法检索未命中。

`conversation_history.read` 新增 `entry_id`，优先按稳定消息 ID 读取，旧 `entry` 编号仍兼容。列表和搜索先分页，再构造响应对象，避免为未返回的全部历史生成大段 JSON。每次请求重新验证已请求的个人记忆／历史结果；旧消息所属时间线被替换或来源消失时返回不可用，不把旧编号误认成另一个消息。此触发是有限的词法启发式，不代替模型按需检索，也不保证所有改写都命中。

## 8.4 稳定记忆快照与当前增量

执行规则不再拼入一份整轮不变的个人记忆摘录。每次模型请求单独组装：

1. **Memory snapshot**：按稳定 ID 排列的精选笔记，带内容版本、来源、分类和到期时间；不随查询改写。
2. **Relevant memory delta**：相关但未在稳定片段出现的笔记／摘录，最多 3 条，不重复注入稳定片段。
3. 必要时的历史检索摘录。

个人记忆文本预算随当前模型输入预算调整，最高 4,200 字符；稳定笔记优先使用其中一半左右，剩余用于相关增量。结构化来源／标题与另列的历史摘录也计入实际请求的上下文预留。无笔记、无相关结果和无历史触发时省略对应片段。任务对话不会自动注入个人事实，可按既有只读工具需要时检索。

片段作为当次请求的补充，不反复追加到任务检查点。因此笔记被修改、遗忘、过期或撤销来源后，下一请求不会携带旧快照；最终人物表达前也重新读取当前个人记忆。来源核对每次建立消息 ID 索引，并复用同一消息的摘要值，避免逐条扫描整段历史。

离线四笔记夹具测得：稳定片段 1,650 字符、请求估算 643 token；改变查询后稳定片段完全相同，构造耗时约 0.26 / 0.22 ms，没有模型调用。这只是主机上的小样，既非真机性能数据，也不代表 DeepSeek 的缓存命中率或实际账单已改善；缓存与真实召回质量仍需后续实测。

## 8.5 成功任务到候选 Skill

`task_state.finish` 的已完成结论通过现有证据检查后，尝试保存一个 `task_experience` 候选。必须引用实际记录的正向工具结果；计划状态、未完成／阻塞结论、空证据和单纯反馈／版本查询不能制造成功经验。结论仍是“有正向工具证据的 Agent 判断”，不是任意用户目标的独立证明。

候选只保存有上限的目标、总结、工具调用 ID 及结果摘要值，不复制原始工具输出；含凭据特征的候选跳过。相同范围／请求／证据 ID 幂等，按聊天最多保留 64 个候选；候选读写受聊天及历史版本隔离。新增失败不重做原操作，也不改变原任务完成结论。

`task_experience`：

- `list(offset)` / `read(experience_id)`：查看候选及当前任务的反馈概览；候选每页最多 8 条。
- `draft`：引用候选，提供英文 `description / triggers / steps / validation / failures`。必须先通过当前接口加载 `skill-creator`。

草稿写到当前工作区 `skill-drafts/<id>/SKILL.md`，经过现有文件工具、项目规则、取消与快照路径；不会覆盖不同内容的已有草稿。此模板路径要求英文 ASCII 指导文本并检查凭据特征，不宣称具备通用自然语言判别能力。特殊引用／素材仍可按现有英文创作要求通过普通文件工具准备。

草稿不自动安装、执行、发布或共享。审查并验证后，仍调用既有 `extensions.install_skill` 导入器；内置 Skill 不能覆盖。Skill creator 的英文指导已补充来源、触发、步骤、验证和失败分支要求，避免将私人对话、一次性流水账或偶然故障沉淀为通用规则。不为旧任务事后伪造候选；旧 Skill 在首次被更新前才建立可核对的基线版本。

## 8.6 使用反馈、比较与恢复

衔接既有两种入口：提交版的 `extensions.load_skill`，以及 Skill 专项正在开发的 `skill` 渐进加载与显式快照。前者在原加载锁内记录内容版本，后者沿用返回的来源／版本；不会增加第二套发现、权限或加载器。旧接口的过期、停用及无版本正文在下一请求撤销指令效力，要求通过当前入口重载；渐进接口继续沿用专项已有的快照失效逻辑。新专项的项目／插件／远端 Skill 通过已加载快照进入同一个观察链。

加载后出现的失败会记录实际调用 ID、结果摘要值、当时已加载的 Skill 来源／版本，并明确 `causality_verified=false`。加载不证明使用，时间相邻不证明 Skill 导致失败。`feedback` 补充具体故障、依赖失效或用户纠正时，要求实际失败调用，或真实用户消息的精确摘录；不会根据一次失败自动改写 Skill。

完整反馈留在当前任务版本，最多 32 条、加载记录最多 8 个。`feedback_history(skill_id, scope, offset)` 可按页读取：

- 默认 `skill_metadata`：跨聊天的简短来源／版本／故障类型／证据指针，每页 8 条，不复制原始反馈文本、目标或用户纠正原文。每个 Skill 最多 32 条，最多保留 64 个 Skill 的索引。
- `current_task`：只读当前任务版本的反馈文本，每页 4 条，不借此读取其他聊天文件。

聊天删除清理其候选与共享反馈指针；共同经历重置清理经验和反馈索引，保留安装的 Skill 及其内容版本档案。用户删除受管 Skill 时同步清理其版本档案和对应共享索引。

受管 Skill 的导入器在发布前保存旧内容和已验证的候选内容，覆盖全部受支持资源，拒绝符号链接／超限资源；不是只备份 SKILL.md。版本以内容摘要标识，元数据保留来源阶段与父版本。未发布的候选可能保留为 `validated_import`，查询时以实际当前内容确定 `current`，不能把候选快照等同于已安装。

`revisions` 查看历史；`compare` 返回变更资源及前后摘要值；`restore(skill_id, revision, expected_revision)` 在现有导入锁内核对当前内容，再走原导入器。后续修改导致摘要不符时拒绝恢复，保留当前文件；内置 Skill 不支持此恢复。启用状态和权限沿用既有配置，不因恢复执行脚本。每个受管 Skill 最多保留 8 个版本，版本档案总目标预算 64 MiB，制作新快照时存在有限临时增量；被逐出的版本明确不可用。

项目、插件和远端源的定义继续由 Skill 专项管理；这里的安装库恢复不假装能替代其源仓库版本控制或远端回滚协议。

## 验证与剩余验收

精确待提交源码在独立 HEAD 副本中构建，48 个相关 JVM 检查通过，验证提交不依赖旁路的未提交 Skill／REA／人物表达改动。相关 JVM 检查覆盖记忆分类、纠正／忘记／过期／来源撤销、原子容量、快照稳定性与成本、历史稳定 ID、证据候选、英文草稿和项目规则保护、真实失败／精确纠正、跨聊天元数据与清理、资源版本摘要、恢复冲突，以及发现／恢复与既有个人对话回归。

另外在包含现有 Skill 专项的工作区构建并运行同一新增核心检查和 Skill 生命周期检查，共 22 个检查通过，验证新旧加载记录、项目快照、资源哈希与原导入入口的衔接。两种配置的检查范围不同，不能将数量相加后称为独立场景数。

本轮没有手机安装、真机检查或真实模型小样；Android 偏好设置下的恢复配置、后台资源、真实召回相关性、长期错误记忆传播、实际 Skill 成功率和 DeepSeek 缓存收益仍需相关场景验收。第一方契约与新增 Skill 指导为英文；用户对话语言、人格和第三方内容保持原有归属。
